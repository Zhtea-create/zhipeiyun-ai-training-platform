# AI 报告改造前的测试准备

本文保留改造前的测试设计和测量记录。报告实现现已优化，ReportBaselineTest 已更新为改造后验收断言；运行结果输出到 `target/report-after/`。改造前证据保留不变，最新对比见 `report-optimization-results.md`。

## 测试边界

- JUnit 直接调用现有 AiServiceImpl 和 AiDataService，使用真实 MyBatis Mapper 与现有 XML SQL。
- 数据位于每个测试独立的 H2 内存数据库（MySQL 兼容模式），测试结束关闭连接后销毁。
- 不启动 Spring Boot，不读取 application.yml，不使用 Windows 中的 AI Key，不连接本机业务 MySQL。
- AiClient 使用固定响应的替身，覆盖未配置 Key、模型成功、模型抛异常和模型返回空内容。此替身用于验证分支、捕获提示词，不代表真实模型回答正确率。
- 用 MyBatis StatementHandler.prepare 拦截器统计实际准备的 SQL，禁止本地缓存隐藏重复查询。报告 Service 当前不带事务，生产调用通常不共享 Mapper SqlSession。
- 计数不含建表和装载数据，不含 Controller、JWT、HTTP 和 AOP 操作日志写入。因此不能与完整接口日志里的 SQL 总数直接混用。
- H2 不能证明 MySQL 执行计划、并发性能或真实模型延迟；这些留待独立 MySQL 测试验证。

## 运行方式

在 PowerShell 中执行：

```powershell
cd D:\codeeee\web-project02\tlias-web-management
$env:JAVA_HOME = 'D:\Java\JDK'
$env:PATH = "$env:JAVA_HOME\bin;$env:PATH"
mvn -B -Dtest=ReportBaselineTest test
```

首次运行需要下载 test scope 的 H2 依赖。指定测试类，避免运行已有的、会加载本机配置的 contextLoads 测试。

产物位于 `tlias-web-management/target/report-baseline/`：

- `summary.md`：各场景的 SQL 和模型调用次数。
- 各场景 Markdown：本次实际 SQL、响应文本以及传给模型的 system 提示词。
- Surefire 结果：`target/surefire-reports/`。

时间戳是报告运行时间，不应作为前后文本完全相同的断言。保存正式基线后，后续改造测试应使用另一输出目录，避免覆盖原始证据。

## 当前行为与后续验收分开

2026-11-08 首次运行：12 个测试通过，0 失败、0 错误。已将汇总及单班成功/异常样本保存到 `docs/report-baseline-before/`，后续保留原样。

| 报告范围 | 未配置 Key | 模型成功 | 模型抛异常 |
|---|---:|---:|---:|
| 全局学员 | 5 | 15 | 15 |
| 指定 101 班 | 7 | 17 | 17 |
| 全局员工 | 4 | 14 | 14 |

表中为 Service 路径准备的 SQL 条数。全局学员报告在模型返回空内容时也为 15 条；空班演示报告为 7 条，不存在班级的演示报告为 6 条。

ReportBaselineTest 是改造前的行为记录测试。它会断言现存的全局数据混入现象，以确保已经复现问题；测试通过不等于班级筛选已经正确。

| 场景 | 改造前应记录的现象 | 后续验收方向 |
|---|---|---|
| 全局学员报告 | 备用报告先查询，模型提示词再次查询 | 按报告类型取数据，成功与降级复用 |
| 员工报告 | 模型输入还包含学员、班级、违纪和日志 | 只包含报告相关数据 |
| 指定 101 班的真实报告 | 模型输入仍包含 Python 班和全局 6 人 | 输入只有 101 班统计，不出现 Python 班学员 |
| 指定 101 班的演示报告 | 聚焦行写 4 人，其余统计仍是全局 | 总数 4、本科 50%、大专和硕士各 25%，只含班内违纪 |
| 空班 103 | 聚焦行 0 人，其余仍全局 | 明确空班，人数 0，无其他班记录，不发生除零 |
| 不存在的班级 999 | 静默生成全局报告 | 明确返回不存在；不能默默切换全局 |
| 模型抛异常 | 返回 mock，带降级提示 | 复用已查数据，不增加补查，不改变统计范围 |
| 模型返回空内容 | 返回备用报告 | 同样复用数据，明确模型不可用状态 |

后续需要明确：单班报告的班级数量按所选班级计为 1（即使为空班）；员工报告不使用 clazzId；begin/end 暂不在本轮改造中增加过滤语义。改造时将这些验收方向变成断言，替换“记录已知问题”的断言，而不是同时保留相反预期。

## 后续 MySQL 性能测试方法

功能基线稳定后，在独立 MySQL 测试库中追加大规模数据测试，禁止往现有业务库批量灌数：

1. 固定 JDK、数据库版本、机器资源、连接池和数据分布，记录表结构与索引。
2. 使用完全相同的数据规模和请求集合运行改造前、后版本；模型接口固定返回，避免网络与生成耗时盖过数据库改进。
3. 预热后重复采样，记录样本数、SQL 次数、数据准备阶段耗时的中位数与 P95；明确并发数和错误数。
4. 单独检查返回数据和降级范围，再比较性能。不能把本轮 H2 测试耗时写成 MySQL 加速指标。
5. 最后少量真实模型冒烟，验证鉴权、协议和最终展示；模型效果及费用另行统计。
