# AI 报告优化结果

## 改动

原流程先查询并生成备用报告，再查询通用快照调用模型。现改为先加载本次请求的 ReportData，再用它生成提示词；需要降级时从同一个对象生成报告，不补查数据库。

- 学员报告只查询学员、班级、学历和违纪；员工报告只查询员工、部门、职位和性别，不再附带其他类型业务数据或操作日志。
- 指定班级时，学历聚合与违纪查询在 SQL 中按 clazz_id 过滤；先过滤再截取违纪前五名。单班人数查询后直接组装班级分布，不再重复查询。
- 空班按一个已存在的班级处理，总人数与平均人数为 0，无其他班级数据。
- 不存在班级抛出 BusinessException，由现有异常处理器返回“班级不存在”，不调用模型，不退回全局报告。
- 报告类型不支持时明确报错；默认类型仍是 student，employee 忽略班级参数，begin/end 本轮未增加语义。
- 模型异常、空白或 null 响应均返回 mock 与降级提示，继续复用已读取的数据。
- 报告的数据查询错误向上传递，不把数据库错误伪装成零人数。聊天快照原有逻辑不在本次改造范围。

## 查询次数对比

同一 H2 固定数据、实际 Mapper SQL、关闭 MyBatis 会话缓存、固定模型替身。统计边界为报告 Service 内 SQL prepare 次数，不含 HTTP、鉴权、AOP 写日志和装载测试数据。

| 场景 | 改造前 | 改造后 | 减少 |
|---|---:|---:|---:|
| 全局学员，模型成功或异常 | 15 | 5 | 66.7% |
| 单班学员，模型成功或异常 | 17 | 4 | 76.5% |
| 员工，模型成功或异常 | 14 | 4 | 71.4% |
| 全局学员，无 Key | 5 | 5 | 0 |
| 单班学员，无 Key | 7 | 4 | 42.9% |
| 员工，无 Key | 4 | 4 | 0 |

这些是数据库访问次数减少，不能解释为响应耗时同比下降。没有进行 MySQL 性能压测、真实模型效果评测，也没有重启现有运行服务。
